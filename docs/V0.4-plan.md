对应：`docs/V0.4-spec.md`（已批准）。

## 一、架构原则

1. **page.tsx 不再堆代码**：人物门户抽出为独立组件 `app/components/person-portal.tsx`，ego 视图抽出 `app/components/person-ego-view.tsx`，旧关系图代码整段删除。
2. **UI 回退不做书卷**：v0.4 已实施的书卷风格 commit（`4a54dcf` + `da8112b`）需要 `git revert`，恢复 v0.3 现代 UI 风格。做旧风格推迟到后续版本。
3. **分析流水线改协议层**：从"单次请求-单次 JSON 响应"改为"暂停-继续"循环模式。引入协议适配层，支持三档模型能力（Tier 1 function calling / Tier 2 JSON 块 / Tier 3 阶段后阻塞）。
4. **数据迁移在 IndexedDB upgrade 中一次完成**：v0.3 旧项目打开时自动迁移 `truth/public→real`、`belief→hidden`、删除 `layer`/`provenance` 相关字段。

## 二、关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 分析流程引入**协议适配层**，支持三档模型能力 | 实时确认需要 function calling（Tier 1）或 JSON 块解析（Tier 2），旧模型 fallback 到阶段后阻塞（Tier 3）。用户在设置页手动选模式。 |
| D2 | 确认队列用**模态弹窗**（非侧边栏）逐个弹出，覆盖全屏或半屏 | 向导式需要聚焦注意力，侧边栏不够醒目；阻塞分析时主内容应置灰/不可交互。 |
| D3 | 阶段状态机**存客户端**（`ProjectAnalysis.stages`），服务端无状态 | 恢复刷新后从 `stages` 读取 `currentStage` 和 `isPaused`，重新触发。服务端只负责单阶段分析。 |
| D4 | 肖像 base64 直接存 `Person.portrait`，不单独存 IndexedDB 对象仓库 | 肖像大小 ≤256×256 压缩后通常 <20KB，直接嵌在 Project JSON 中足够，无需单独仓库。 |
| D5 | 关系图板块**只删除旧关系图代码**，线索图和时间线的 React Flow 保留 | 用户只要求改关系图为人物门户，线索图和时间线不动功能。 |
| D6 | **UI 回退不做书卷风格** | v0.4 已实施的书卷 commit 需要 revert。做旧风格等用户素材定稿后单独出补丁文档。 |
| D7 | 检索召回按人/按对的块合并后**去重**，总预算 ≤30 块 | 按人召回（核心人物数 × 3 块）+ 按对共现（人物对数 × 2 块）可能 >25，去重后压到 20~30。如果仍 >30，截断到 30（按 BM25 分数排序）。 |
| D8 | 关系抽取 prompt 的 provenance 概念**保留在 people/timeline/clues 阶段**，只在 relations 阶段去掉 | overview/people/timeline/clues 仍需 `provenance`（source/inference/conflict），不能全局删。relations 阶段的新 prompt 只输出 `real`/`hidden` 二元标记。 |
| D9 | 地点提取放在 **clues 阶段**（不新增 place 阶段），提取到的 place targets 进入确认队列 | 避免新增独立阶段和 API 调用。clues 阶段已有 `place` 类型 target，复用即可。 |
| D10 | 肖像上传用 `<input type="file" accept="image/*">` + 前端 `canvas` 压缩，不引入新依赖 | 纯浏览器 API 即可，无需额外库。 |
| D11 | 协议适配层新建 `lib/model-adapter.ts` | 抽象三档模型能力，`route.ts` 根据用户选择的 `confirmMode` 路由到对应处理逻辑。 |
| D12 | `ask_user` 工具定义统一 | Tier 1 用原生 function calling；Tier 2 在 system prompt 中教模型输出 `<<ASK_USER>>{json}<</ASK_USER>>` 标记块；Tier 3 不注入工具，阶段后阻塞。 |

## 五、分析流水线控制流改造

### 当前控制流（v0.4 已实施）

```
用户点击"开始分析"
  → runStage("people") → 完成 → 检查 reviewItems → 阶段后阻塞弹窗
  → runStage("relations") → 完成 → 自动继续
  → runStage("timeline") → 完成 → 自动继续
  → runStage("clues") → 完成 → 检查 reviewItems → 阶段后阻塞弹窗
```

**问题**：用户反馈"整个分析跑完才确认"，实际是阶段后阻塞，不是用户想要的实时确认。

### 目标控制流（v0.4 补丁：实时确认）

#### Tier 1（DeepSeek 等支持 function calling）

```
用户点击"开始分析"，confirmMode="tier1"
  → POST /api/model (action=analyze, stage="people", confirmMode="tier1")
  → 服务端注入 ask_user 工具定义，调用模型
  → 流式解析：
      - 检测到 tool_call(ask_user) → 立即中断，返回 { type:"ask_user", callId, question, options, context }
      - 模型正常完成 → 返回 { type:"complete", data:{...} }
  → 客户端收到 ask_user → 弹出 ConfirmWizard
  → KP 裁决 → POST /api/model (action=continue, callId, answer, previousMessages)
  → 服务端把裁决作为 tool_response 注入 → 模型继续生成 → 循环
  → 模型最终完成 → 返回 { type:"complete", data:{...} }
  → 客户端处理 data，继续下一阶段
```

#### Tier 2（Kimi 等不支持原生工具调用）

```
同 Tier 1，但：
  → 服务端在 system prompt 中教模型输出 <<ASK_USER>>{json}<</ASK_USER>> 标记块
  → 流式解析检测标记块 → 中断返回
  → continue 时把裁决结果作为新 user message 注入（而非 tool_response）
```

#### Tier 3（旧模型 fallback）

```
保持现有 v0.4 已实施的阶段后阻塞逻辑不变
  → 阶段跑完 → 检查 reviewItems → 批量弹窗
```

### 协议适配层设计（`lib/model-adapter.ts`）

```typescript
export type ConfirmMode = "tier1" | "tier2" | "tier3";

export interface AskUserCall {
  callId: string;
  question: string;
  options: string[];
  context: string;
}

export interface ModelStreamEvent {
  type: "ask_user" | "content" | "complete";
  askUserCall?: AskUserCall;
  content?: string;
  data?: unknown;
}

// 构建请求参数（根据 tier 决定是否注入 tools 或 JSON 块指令）
export function buildModelRequest(
  stage: AnalysisStage,
  confirmMode: ConfirmMode,
  previousMessages?: Message[]
): ModelRequest {
  if (confirmMode === "tier1") {
    return { ...base, tools: [ASK_USER_TOOL_DEF] };
  } else if (confirmMode === "tier2") {
    return { ...base, system: base.system + ASK_USER_JSON_INSTRUCTION };
  }
  return base; // tier3 不注入
}

// 解析模型响应，检测中断信号
export function parseStreamResponse(
  raw: ModelRawResponse,
  confirmMode: ConfirmMode
): ModelStreamEvent {
  if (confirmMode === "tier1") {
    const toolCall = raw.choices[0].message.tool_calls?.[0];
    if (toolCall?.function?.name === "ask_user") {
      return { type: "ask_user", askUserCall: parseToolCall(toolCall) };
    }
  } else if (confirmMode === "tier2") {
    const content = raw.choices[0].message.content;
    const match = content.match(/<<ASK_USER>>(.*?)<</ASK_USER>>/s);
    if (match) {
      return { type: "ask_user", askUserCall: parseJsonBlock(match[1]) };
    }
  }
  return { type: "complete", data: parseJsonContent(raw.choices[0].message.content) };
}

// 构建 continue 请求（把裁决结果注入）
export function buildContinueRequest(
  callId: string,
  answer: string,
  previousMessages: Message[],
  confirmMode: ConfirmMode
): ModelRequest {
  if (confirmMode === "tier1") {
    return { messages: [...previousMessages, { role: "tool", tool_call_id: callId, content: answer }] };
  } else {
    return { messages: [...previousMessages, { role: "user", content: `KP 裁决：${answer}` }] };
  }
}
```

### `ask_user` 工具定义

```typescript
const ASK_USER_TOOL_DEF = {
  type: "function",
  function: {
    name: "ask_user",
    description: "当遇到信息冲突、不确定信息、或需要 KP 裁决时调用此工具暂停分析并询问 KP",
    parameters: {
      type: "object",
      properties: {
        question: { type: "string", description: "向 KP 提出的问题" },
        options: { type: "array", items: { type: "string" }, description: "可选的裁决选项" },
        context: { type: "string", description: "为什么需要询问，原文依据是什么" }
      },
      required: ["question", "context"]
    }
  }
};
```

### 恢复逻辑（刷新后）

```
加载项目 → 读取 stages[currentStage].status
  → "paused" 且有 pendingAskUserCall → 弹出 ConfirmWizard 恢复确认
  → "paused" 且无 pendingAskUserCall → 弹出该阶段 pending review items 向导（Tier 3 兼容）
  → "running" → 视为丢失，改 "idle"，提示用户手动重跑
  → "complete" → 找到下一个 "idle" 阶段 → 提示用户继续
```

### 阶段顺序与阻塞策略

| 阶段 | 阻塞？ | 触发条件 |
|---|---|---|
| overview | 否 | 自动继续 |
| people | 是 | 模型调用 ask_user（Tier 1/2）或有 pending review items（Tier 3） |
| relations | 否 | 自动继续 |
| timeline | 否 | 自动继续 |
| clues | 是 | 同 people |

### 设置页模式选择

设置页新增"确认模式"选择器：
- **实时确认（推荐，需 DeepSeek/OpenAI 等支持工具调用的模型）** → `confirmMode="tier1"`
- **准实时确认（Kimi/Qwen 等支持结构化输出的模型）** → `confirmMode="tier2"`
- **阶段后确认（旧模型/本地模型）** → `confirmMode="tier3"`

默认 `tier1`，用户可切换。`confirmMode` 存储在 `Project.settings` 或全局设置中。

```typescript
type PortalView = "gallery" | "ego";

const [portalView, setPortalView] = useState<PortalView>("gallery");
const [selectedPersonId, setSelectedPersonId] = useState<string | null>(null);

  setEgoHistory(prev => {
    const next = prev.slice(0, -1);

    if (next.length === 0) setPortalView("gallery");
    return next;
  });
};
```

## 八、检索召回改进

### 当前实现（`lib/retrieval.ts`）

```typescript
// 约 163 行，relations 阶段 query：
const query = `人物 关系 联盟 敌对 秘密 + ${personNames.join(" ")}`;
```

### 目标实现

```typescript
// 按人召回：每个核心人物（含 aliases）分别检索 Top 3
const personChunks = [];
for (const person of corePeople) {
  const query = `${person.name} ${person.aliases.join(" ")} 关系 联盟 敌对 秘密 刺杀 谋杀 阴谋 计划 意图 勒索 跟踪 背叛 献祭 威胁 监视 仇恨 保护 利用`;
  const chunks = bm25Search(query, allChunks, 3);
  personChunks.push(...chunks);
}

// 按对共现召回：核心人物对双词检索
const pairChunks = [];
for (let i = 0; i < corePeople.length; i++) {
  for (let j = i + 1; j < corePeople.length; j++) {
    const query = `${corePeople[i].name} ${corePeople[j].name}`;
    const chunks = bm25Search(query, allChunks, 2);
    pairChunks.push(...chunks);
  }
}

// 合并去重，按分数排序，取 Top 20~30
const merged = mergeAndDeduplicate([...personChunks, ...pairChunks]);
const result = merged.slice(0, 30);  // 硬上限 30
```

### 性能考量

- 核心人物通常 ≤20 人，按人召回 = 20×3 = 60 次 BM25 查询，但 BM25 是本地计算（无外部请求），60 次在浏览器中可接受（毫秒级）。
- 人物对：20 人 = 190 对，190×2 = 380 次 BM25 查询。可能稍重，但仍是纯本地计算。若人物 >30，只取前 30 个核心人物做配对。
- 优化：先按人召回，如果按人召回已覆盖 30 块，则跳过按对召回；或者按对召回只取核心人物对（importance="core"|"important" 的）。

决策：**按对召回只取重要人物对**（importance ≠ "minor"），减少计算量。
