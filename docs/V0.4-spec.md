# 守秘人图谱 v0.4 需求规格说明

## 版本目标

从"全图画布"转向**人物门户导航**，以 KP 上帝视角为设计核心，全 App 统一书卷视觉风格。同步解决 v0.3 遗留的数据丢失、召回不足、分析流程不可控问题。

---

## 一、功能需求

### F1. 人物门户（取代旧关系图）

**F1.1 人物肖像画廊**
- 外层入口为人物肖像卡片网格/画廊，全部人物一次展示
- 每张卡片：人物肖像（圆形/圆角边框，书卷风格画框）+ 人物名 + 可省略的简短身份标签
- **无肖像时留白**（显示姓名首字母或剪影占位，不强制填充）
- 书卷风格：泛黄卡片底、古典衬线字体、轻微纹理
- 支持搜索/筛选（按姓名、组织、身份）

**F1.2 人物 ego 视图**
- 点击肖像卡片进入该人物的 ego 视图
- 顶部：中心人物大肖像 + 姓名 + 身份描述 + 编辑按钮（含肖像上传入口）
- 下方：**关联人物肖像列表**——与该人物有直接关系的所有人物，每人一张小肖像卡片
- 每张关联卡片显示：小肖像 + 姓名 + **关系类型标记**（`real` 默认色 / `hidden` 异色标注）+ 关系简述
- 列表式，无画布、无边线、无节点布局算法

**F1.3 门户导航**
- 点击 ego 视图中的任何关联人物肖像 → 进入该人物的 ego 视图（push 导航）
- 支持**返回栈**（返回上一人、返回画廊）
- 导航历史在 session 内保持，刷新后重置到画廊（不要求持久化导航栈）

**F1.4 肖像上传**
- 人物编辑面板增加"上传肖像"按钮
- 接受常见图片格式（jpg/png/webp），前端压缩至 ≤256×256，转 base64 存 IndexedDB `Person.portrait`
- 无肖像时 `portrait` 为 `undefined`，UI 渲染占位
- 删除人物时同步删除肖像数据
- 预留 `Person.portraitSource` 字段（`"manual" | "extracted" | "generated"`），为后续 PDF 提取/AI 生成预留

### F2. 关系体系简化（数据层）

**F2.1 关系类型二元化**
- `Relationship.type` 从多层级（truth/public/belief/...）简化为**仅两种**：
  - `real`：模组文本明确公开陈述的关系（玩家可直接获知）
  - `hidden`：模组文本暗藏的秘密关系（仅 KP 知道，对玩家保密）
- 所有存量数据的 truth/public 合并为 `real`，belief/AI推测 合并为 `hidden`（迁移规则）
- **废弃** `source`（truth/public/belief 等来源维度）和 `provenance`（AI推测标记）字段

**F2.2 同对同类型去重**
- 去重 key：`${sourceId}\0${targetId}\0${type}`
- 同一对人、同一类型（real 或 hidden）只保留**第一条**关系描述
- 同一对人、**不同类型**（real + hidden）**保留两条**，在 ego 视图中分别展示
- 去重在分析阶段入库前完成，保证数据干净

**F2.3 关系抽取 Prompt 改写**
- relations 阶段 prompt 不再要求输出多层来源，只要求判断：
  - 这段描述里的关系，模组是**公开写的**还是**秘密写的**？
  - 公开 → `real`，秘密 → `hidden`
- prompt 中显式列举关系范畴（身份/血缘、社会/组织、情感/态度、**行动/意图**、秘密/把柄），强调"单向意图和计划也是关系"
- 检索词保留 v0.3.1 扩充的 14 个敌对/意图动词

### F3. 分析流程：实时确认队列

**F3.1 实时暂停机制**
- 模型在分析过程中遇到**信息冲突、不确定信息、需要 KP 裁决**时，**立即暂停当前阶段**，弹出确认弹窗
- 不是"阶段跑完再统一弹窗"，而是**模型主动调用中断**
- KP 处理完一项 → 模型基于裁决结果继续生成
- 阻塞阶段：**人物识别（people）**、**线索（clues）**
- 不阻塞阶段：**时间线（timeline）**、**关系（relations）**、**概览（overview）**

**F3.2 三档模型兼容**
系统支持三档模型能力，用户在设置页**手动选择**模式：

| 档位 | 适用模型 | 实现方式 | 用户体验 |
|---|---|---|---|
| **Tier 1：实时确认** | DeepSeek、OpenAI、Claude 等支持 function calling 的模型 | 模型调用 `ask_user` 工具，服务端中断流，弹窗给 KP | 实时暂停（最优） |
| **Tier 2：准实时确认** | Kimi、Qwen 等支持结构化输出但不支持原生工具调用的模型 | 模型输出中嵌入 `<<ASK_USER>>{json}<</ASK_USER>>` 标记块，服务端解析后中断 | 准实时暂停（延迟 1~2 秒） |
| **Tier 3：阶段后阻塞** | 不支持结构化的旧模型、本地小模型 | 阶段跑完后统一弹窗（v0.4 已实现的逻辑） | 阶段后阻塞 |

- 设置页显示模型能力说明，用户根据自己的模型选择模式
- 默认推荐 Tier 1（DeepSeek），用户可切换

**F3.3 向导式审查**
- 暂停后，弹出**单个**待确认项（模态弹窗），只给 KP 看一项
- KP 操作：**确认**（接受为正式数据）、**否决**（丢弃）、**修改**（编辑后接受）
- 处理完一项 → 模型基于裁决结果继续生成，或弹出该阶段**下一个**待确认项
- 整个分析过程中，activityLog 实时记录"阶段 X 暂停 - 第 M 项待确认"

**F3.4 阶段重跑**
- 已完成的阶段可单独重跑（如：只重跑关系阶段，不重新识别人物）
- 重跑某阶段时，该阶段之前产生的数据（如人物列表）作为输入，不重新生成

### F4. 检索召回改进（关系图报告 P1-P3）

**F4.1 按人召回**
- relations 阶段：对每个核心人物（含别名），单独用 BM25 检索取 Top 3~5 块
- 合并所有人物的召回块，去重
- 保证每个核心人物的上下文都在，不受人名拼接稀释影响

**F4.2 按人物对共现召回**
- 对核心人物对（如 A+B），用双词检索 `A B` 取共现块
- 两人同框的块几乎必然含关系信息，权重高于单人文本
- 共现块与按人召回块合并去重

**F4.3 块预算提升**
- 关系阶段检索块预算从 Top 12 提升至 **20~25**
- 20×500 字 ≈ 1 万字，主流模型上下文均吃得下
- 预算提升仅作用于 relations 阶段，其他阶段保持 12 不变（避免 token 浪费）

### F5. UI 风格（v0.4 暂不做）

**状态**：v0.4 先回退到 v0.3 现代 UI 风格，书卷/做旧风格推迟到后续版本。

- v0.4 已实施的书卷风格 commit（`4a54dcf` + `da8112b`）需要 `git revert`
- 做旧书页素材由用户提供，后续版本单独出补丁文档实施
- 补丁范围：只在"文本内容区域"（线索文本、待确认弹窗描述、模组原文引用等）做旧，UI 外壳（按钮、面板边框、背景底色、导航栏）保持现代风格

### F6. 地图（最小数据版）

**F6.1 地点实体提取**
- 分析流程的 clues 阶段或独立 place 阶段，从文本中提取地点实体
- 地点进待确认队列（F3.1 阻塞），KP 确认后才成为正式 `Place` 实体
- 每个地点含：`name`（名称）、`description`（描述）、`regionHint`（文本中提到的区域/方位）

**F6.2 地点数据存储**
- `ProjectAnalysis.places` 存储确认后的地点数组
- IndexedDB `PLACES` 对象仓库（预留，与人物/线索同层级）
- 地点数据为后续 v0.5 的"藏宝图风格画布"做准备，v0.4 **不实现**任何可视化

## 二、非功能需求

| ID | 需求 | 说明 |
|---|---|---|
| N1 | 纯本地优先 | 肖像存 IndexedDB，不依赖外部图床；书卷风格纯 CSS，不加载外部字体文件（优先系统自带衬线字体） |
| N2 | 隐私不降 | 不引入外部地图瓦片、不引入外部 CDN 字体、分析流程不泄露模组内容 |
| N3 | 可恢复性 | 分析阶段阻塞后，用户刷新页面应能从当前阶段恢复（不丢失已确认数据，不重复已跑阶段） |
| N4 | 性能 | 人物画廊 ≤50 人时渲染流畅（不卡顿）；ego 视图关联列表 ≤30 人时不分页 |
| N5 | 兼容性 | 旧项目数据（v0.3 的 truth/public/belief 关系）迁移至 real/hidden 无丢失 |

| 事项 | 说明 | 去向 |

| 时间线确认队列 | 用户明确不需要 | 时间线阶段自动跑过，不阻塞 |

## 四、数据模型变更

### 变更一览

| 实体 | 字段 | 变更 | 说明 |
|---|---|---|---|
| `Person` | `portrait?: string` | **新增** | base64 编码的肖像图，≤256×256 |
| `Person` | `portraitSource?: string` | **新增** | 预留：`"manual"` / `"extracted"` / `"generated"` |
| `Relationship` | `type` | **改枚举** | 从 `truth`/`public`/`belief`/`inferred` 简化为 `real` / `hidden`；存量迁移：truth/public → real，belief/inferred → hidden |
| `Relationship` | `source` / `provenance` | **删除** | 不再需要来源分层和 AI 推测标记 |
| `ProjectAnalysis` | `places` | **新增** | `Place[]` 数组，地点实体（确认后） |
| `ProjectAnalysis` | `analysisState` | **新增** | 阶段步进状态：`{ currentStage: string, isPaused: boolean, pendingReviews: ReviewItem[] }`，用于恢复 |
| `ReviewItem` | `type` | **扩展** | 增加 `"place"`，地点提名进确认队列 |
| `Place` | `regionHint` | **新增** | 文本中提到的区域/方位描述，用于后续 v0.5 画布定位 |

### 数据迁移

- v0.3 旧项目打开时，`Relationship.type` 迁移：truth / public → `real`；belief / 所有 inferred → `hidden`；`source` / `provenance` 字段丢弃（可在 IndexedDB upgrade 中 `delete`）
- `Person.portrait` / `portraitSource` 默认 `undefined`
- `ProjectAnalysis.places` 默认 `[]`
- `ProjectAnalysis.analysisState` 默认 `{ currentStage: "", isPaused: false, pendingReviews: [] }`

## 五、分析流水线架构变更

### 当前（v0.3 + v0.4 已实施）

```
客户端 → POST /api/model (action=analyze, stage="people", projectData)
服务端 → 执行单个阶段，返回 JSON { data: { people: [...], reviewItems: [...] } }
客户端 → 检查 reviewItems → 向导式弹窗（已实现，但是阶段后阻塞）
```

### 目标（v0.4 补丁：实时确认）

```
客户端 → POST /api/model (action=analyze, stage="people", projectData, confirmMode="tier1"|"tier2"|"tier3")
服务端 → 调用模型，传入 ask_user 工具（Tier 1）或 JSON 块指令（Tier 2）
       → 流式解析模型输出：
           - 检测到 tool_call（Tier 1）→ 立即中断，返回 { type: "ask_user", callId, question, options, context }
           - 检测到 <<ASK_USER>>{json}<</ASK_USER>> 块（Tier 2）→ 立即中断，返回同上
           - 模型正常完成 → 返回 { type: "complete", data: {...} }
客户端 → 收到 ask_user → 弹出 ConfirmWizard → KP 裁决 → POST /api/model (action=continue, callId, answer, previousContext)
服务端 → 把裁决结果作为 tool_response 或上下文注入 → 模型继续生成 → 循环
```

### 关键约束

- 每个阶段调用仍是**独立的 HTTP 请求**，但实时确认模式下可能**多次请求**（暂停-继续循环）
- 服务端**不持久化**分析中间状态，恢复靠客户端保存的 `analysisState`
- Tier 3（阶段后阻塞）保留现有 v0.4 已实现的逻辑，作为 fallback
- 模型能力由用户在设置页**手动选择**，系统不自动探测

## 六、验收标准（AC1~AC10）

| AC | 验证方式 | 可观测标准 |
|---|---|---|
| **AC1** | 浏览器实测 | 打开人物门户 → 画廊展示所有人物肖像卡片（有肖像的显示图，无肖像的显示占位），书卷风格底色/字体/边框可见 |
| **AC2** | 浏览器实测 | 点击任意人物肖像 → 进入 ego 视图，中心人物大卡片 + 下方关联人物列表；关联人物卡片显示关系类型（real/hidden 颜色不同） |
| **AC3** | 浏览器实测 | ego 视图中点击关联人物 → 进入该人物 ego 视图；点击返回 → 回到上一人；连续跳转 3 层无异常 |
| **AC4** | 浏览器实测 | 人物编辑面板"上传肖像" → 选图 → 保存 → 画廊和 ego 视图均显示该肖像；删除人物后肖像数据同步清除 |
| **AC5** | 浏览器实测 + 代码审查 | 同对人物有多条关系（如 A→B 既有 real 又有 hidden）→ 两条均在 ego 视图中展示；同类型重复只显示一条 |
| **AC6** | 浏览器实测 | 实时确认模式（Tier 1）：跑人物分析 → 模型遇到冲突立即暂停弹出确认弹窗 → KP 裁决后继续生成 → 不再是阶段跑完才弹窗。Tier 3 模式：阶段跑完后弹窗（现有逻辑） |
| **AC7** | 运行代码 | `lib/retrieval.ts` 中 relations 阶段召回逻辑：含"刺杀/阴谋/计划"等词的剧本段落，BM25 召回 Top 20 块中包含该段落 |
| **AC8** | 运行代码 | 按人召回 + 人物对共现召回后，合并块数 ≥ 按旧 query 召回的块数，且不遗漏核心人物上下文 |
| **AC9** | 浏览器实测 | UI 风格为现代风格（非书卷），v0.4 已实施的书卷 commit 已 revert；人物画廊和 ego 视图渲染正常 |
| **AC10** | 浏览器实测 + IndexedDB 检查 | 分析完含地点的剧本 → 地点出现在待确认队列 → 确认后 → devtools IndexedDB `PLACES` 仓库出现对应记录；v0.4 无地图可视化页面 |
