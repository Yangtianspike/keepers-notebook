# 守秘人图谱 v0.5 技术设计（Plan）

对应：`docs/V0.5-spec.md`（已批准）。

---

## 一、架构原则

1. **分析流程重构为主**：`AnalysisStage` 枚举从 5 改为 7，`stageInstructions` 重写 7 个阶段的 prompt，`runStage` 控制流调整阶段顺序和阻塞策略。
2. **砍模块要干净**：删除人物门户/线索图/时间线/地图的组件文件和 page.tsx 中的引用，不留废弃代码。
3. **幕模块新建独立组件**：`ActTreeView`（树状图）+ `ActDetailView`（幕详情），不往 page.tsx 堆代码。
4. **章节总结复用分析结果**：7 阶段跑完后，用已有数据组装章节总结，不需要重新调用模型（或最多一次轻量调用补充）。
5. **UX 修复改动最小**：只调整 `continueRealtimeAnalysis` 的响应处理顺序。
6. **数据迁移在 IndexedDB upgrade 中完成**：DB_VERSION 3→4，迁移旧 relations/timeline 到 acts。

## 二、关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | `AnalysisStage` 枚举直接替换 | 5→7 阶段是全量替换，不是新增 |
| D2 | 幕阶段分两次模型调用 | 第一次生成幕骨架（列表+分支），第二次填充每幕详情。避免单次输出过长 |
| D3 | 章节总结作为幕阶段后的自动步骤 | 不新增独立阶段，7 阶段跑完后自动用已有数据组装 |
| D4 | 肖像上传移到幕的人物卡 | 人物门户砍掉后，人物编辑入口在幕详情的人物卡里 |
| D5 | 树状图用 React Flow | 已有依赖，节点=幕，边=分支条件 |
| D6 | 旧 relations 迁移到幕 | 按 sourceId/targetId 找到涉及的人物，把关系分配到第一个包含该人物的幕 |
| D7 | 旧 timeline 迁移到幕的 keyEvents | 每个 timeline event 转为 KeyEvent，按时间顺序分配到幕 |
| D8 | `runStage` 函数保持现有结构 | 只改阶段枚举和 prompt，控制流逻辑（检索/调用/解析/合并）不变 |
| D9 | 砍掉的组件文件直接删除 | person-gallery.tsx/person-ego-view.tsx/person-portrait.tsx/atlas-map.tsx 删除 |
| D10 | 幕后真相页（OverviewView）保留并扩展 | 显示阶段1-6的全局结果（故事背景/时间地点/核心人物/人物经历/开篇钩子/线索） |

## 五、分析流程 prompt 设计

### 阶段1：故事背景（background）

```
分析整个剧本，返回故事核心、起因、历史、现状、结局。
```

### 阶段2：时间地点（timeplace）

```
汇总剧本中的时间信息和地点信息。
返回时间线概要 + 地点列表（含名称/描述/方位）。
```

### 阶段3：核心人物（characters）

```
识别所有有名人物（同 v0.4 的 people 阶段，保留 importance 分级）。
实时确认：遇到信息冲突时调用 ask_user。
```

### 阶段4：人物经历与动机（characterArcs）

```
基于已确认的人物列表，分析每个人物在故事中的经历和动机。
返回每个人物的经历概述 + 动机详解。
```

### 阶段5：开篇钩子（openingHook）

```
分析剧本开篇，提取吸引玩家入局的钩子。
返回开篇钩子描述。
```

### 阶段6：关键线索安排（clues）

```
梳理剧本中的调查线索（同 v0.4 的 clues 阶段）。
实时确认：遇到信息冲突时调用 ask_user。
```

### 阶段7：幕（acts）

**第一次调用（骨架）**：
```
基于前面的分析结果（故事背景/人物/线索/地点），将剧本划分为多个幕。
每幕包含：标题、序号、地点、时间、涉及人物、涉及线索。
分支：每幕结尾的分支条件，指向下一幕。
返回 Act[] 骨架。
```

**第二次调用（填充）**：
```
为每个幕填充详细描述和阶段性重要事件点（含 Boss 数值）。
返回每幕的 description + keyEvents。
```

## 六、幕模块组件架构

### ActTreeView（树状图）

```
React Flow 画布
├── 节点：幕（显示标题+序号）
├── 边：分支条件（显示条件文字）
├── 交互：
│   ├── 点击节点 → 跳转到 ActDetailView
│   ├── 缩放/平移
│   └── 自动布局（dagre，从左到右）
└── 工具栏：切换列表视图/树状图视图
```

### ActDetailView（幕详情）

```
幕详情面板
├── 顶部：幕标题 + 序号 + 编辑按钮
├── 基本信息：地点 + 时间
├── 人物卡列表（分层）：
│   ├── 核心人物（importance=core）
│   ├── 重要人物（importance=important）
│   └── 次要人物（importance=minor）
│   每张卡：姓名 + 肖像（可上传） + 在该幕中的角色
│   点击卡 → 查看该人物在其他幕的出现记录
├── 线索卡列表（分层）：
│   ├── 关键线索（importance=key）
│   ├── 次要线索（importance=secondary）
│   └── 其他线索（importance=other）
│   每张卡：线索名 + 获取方式 + 在该幕中的作用
├── 分支结局：
│   ├── 分支条件列表
│   └── 每个分支指向的下一幕（可点击跳转）
├── 阶段性重要事件点：
│   └── 每个事件：标题 + 类型 + 描述 + CoC 数值
└── 幕描述：文字描述
```

## 七、数据迁移（DB v3→v4）

```typescript
// storage.ts onupgradeneeded
if (oldVersion < 4) {
  // 遍历所有项目
  for (const project of allProjects) {
    const analysis = project.analysis;
    
    // 1. relations → acts
    const acts: Act[] = [];
    if (analysis.relations?.length) {
      // 按人物对分组，分配到幕（简化：全部放到一个"迁移幕"中）
      acts.push({
        id: crypto.randomUUID(),
        title: "迁移的关系数据",
        sequence: 1,
        time: "未知",
        personIds: [...new Set(analysis.relations.flatMap(r => [r.sourceId, r.targetId]))],
        clueIds: [],
        branches: [],
        keyEvents: [],
        description: `从 v0.4 迁移的 ${analysis.relations.length} 条人物关系`,
      });
    }
    
    // 2. timeline → acts.keyEvents
    if (analysis.timeline?.length) {
      analysis.timeline.forEach(event => {
        acts.push({
          id: crypto.randomUUID(),
          title: event.title,
          sequence: acts.length + 1,
          time: event.date || "未知",
          personIds: [],
          clueIds: [],
          branches: [],
          keyEvents: [{
            title: event.title,
            type: "checkpoint",
            description: event.summary,
          }],
          description: event.summary,
        });
      });
    }
    
    // 3. 删除旧字段
    delete analysis.relations;
    delete analysis.timeline;
    delete analysis.relationshipLayout;
    delete analysis.clueLayout;
    
    // 4. 新增字段
    analysis.acts = acts;
    analysis.chapterSummaries = [];
    analysis.timePlace = analysis.timePlace ?? { timeline: "", places: analysis.places };
    analysis.characterArcs = analysis.characterArcs ?? [];
    analysis.openingHook = analysis.openingHook ?? "";
  }
}
```

const continueRealtimeAnalysis = async (answer: string, keeperNote?: string) => {

    const response = await fetch("/api/model", { /* ... */ });
    const payload = await response.json();
    
    if (payload.type === "ask_user") {
      await persistProject({ /* ... pendingAskUserCall: payload ... */ });
      setWizardStage(pending.stage);
    } else {
      await runStage(pending.stage, resumedProject, payload.data);
    }
  } finally {

## 九、风险与对策

| 风险 | 严重度 | 对策 |
|---|---|---|
| runStage 函数 625 行改动引入回归 | 高 | 只改阶段枚举和 prompt，控制流逻辑不变；逐段改，每段 build 验证 |
| 幕阶段两次调用模型耗时过长 | 中 | 第一次骨架调用快速返回，第二次填充可并行 |
| 数据迁移导致旧项目数据丢失 | 高 | 迁移前备份，迁移后验证；relations/timeline 不删除只转换 |
| 砍掉4个模块误删共享代码 | 中 | 逐个删除，每次 build 验证；保留 confirm-wizard 等共享组件 |
| 幕树状图 React Flow 节点过多 | 低 | 幕通常 ≤20，dagre 布局能处理 |
