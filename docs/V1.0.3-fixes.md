# 守秘人笔记本 v1.0.3 补丁

> 状态：已实现
> 基线版本：v1.0.2
> 触发问题：展示材料类图片提取失败、扫描卡顿、空白图层混入结果

## 版本主题

PDF 图片提取的超时与并发策略修正、空白图层过滤，以及新增「整页导出」用于保留排版的展示材料。

复现文件：`样本 A.pdf`（63 页）、`样本 B`。

---

## 一、问题与根因

### B1 展示材料整页大图提取不出来

现象：扫描后只能拿到一张小图（无名猎兽），其余展示材料全部缺失。

根因：`readPdfObject` 给每张图片的解码只留了 **1200ms**。

```214:214:app/components/source-image-extractor.tsx
    const timeout = window.setTimeout(() => finish(null), 1200);
```

实测该模组内嵌图尺寸远超大图常规值：

| 页 | 尺寸 | 数据量 |
| --- | --- | --- |
| p3 | 1441×1192 | 5.1 MB |
| p4 | 2602×1553 | 12.1 MB |
| p5 | 2595×1392 | 10.8 MB |
| p6 | 1298×3456 | 13.5 MB |

这些图解码必然超过 1.2 秒，超时后回调收到 `null`，图片被**静默丢弃**且没有任何提示。

### B2 扫描过程卡住

现象：扫描 `样本 B` 时停在第 2 页不动，状态文字停在「正在扫描第 2 页（2 / 35），已找到 3 张…」。

根因：修完 B1 后单张超时放宽到 30s，而逐张**串行**读取时，遇到永远不解码的对象就要死等满 30 秒；总耗时随图片数量线性放大。

### B3 大量空白图片混入结果

现象：提取结果里出现大量几乎全白的图片，只有边框或分隔线。

根因：`isBlankOrBlackLayer` 只判断「全黑蒙版」，对**全白底图**和**内容占比极低**的图层没有处理。

实测这些图层确实没有内容：

```
img_p3_1 (2602x1553)  平均亮度 254.0  非白像素 0.5%  三通道完全相同 100%
img_p2_2 (1441x1192)  平均亮度 252.4  非白像素 1.3%  三通道完全相同 100%
img_p9_1 (1416x2371)  平均亮度 253.3  非白像素 0.7%  三通道完全相同 100%
```

### B4 展示材料类内容无法交付

现象：即使成功提取到图层，导出结果也只有外框和标题，框内正文缺失。

根因：展示材料是「**图片图层 + 文本层**」混合排版 —— 框线与标题在图像层，正文在文本层。只提取内嵌图片**永远拿不到完整内容**。

验证：`展示材料 1` 的正文全部存在于文本层。

```
"来自不同报纸的头条"  → 命中 p3
"旧城区发生两起命案"  → 命中 p3
"旧城区神秘死亡事件"  → 命中 p3
"警方受挫"            → 命中 p3
```

## 二、修复要求

### F1 修正图片解码超时（必须）

- 解码超时最终定为 **1500ms**。过程中曾一度放宽到 15000ms，实测后确认该判断有误并回退。
- 实测依据：本模组内最大的图片（`2602x1553`、`1298x3456`）解码仅需 **36~46ms**，其余对象都是毫秒级；1200ms 从来不是瓶颈，「大图会超时」是错误推断。
- 超时值的真实作用是「个别对象永不回调时的兜底」：**设得越大，扫描被拖慢得越明显**（逐页累计）。1500ms 相对实测值已留出约 30 倍余量。

### F2 图片改为并发读取（必须）

- 每页先 `Promise.all` 并发请求该页全部图片对象，再按顺序处理结果。
- 总耗时由「图片数 × 超时」降为「单张超时」，不再随图片数量线性放大。

### F3 过滤空白与低内容图层（必须）

- 同时过滤**全黑**（蒙版层）与**全白**（空白底图）。
- 新增内容占比判断：亮度低于阈值的像素不足 2% 时判定为「只剩边框或分隔线」，不予保留。
- 判据必须按采样图计算，不能只看均值，避免把「大面积留白但确有插画」的图误删。

### F4 整页导出与框选（已回退，不实现）

先后尝试了三种方案，结论都是**方向不对，已全部移除**：

1. **整页导出**（`page.render()`）—— 导出整页后用户仍需自行裁剪，与直接在 PDF 阅读器里截图没有区别，没有实际价值。
2. **自动检测矩形框并按框裁剪** —— 从 `constructPath` 能取到准确的框坐标（实测 `展示材料 1` 的框为 226×194，双重边框），但裁剪出的结果仍不满足使用预期。
3. **手动框选** —— 交互上比整页导出更麻烦，同样没有解决问题。

**根本原因**：展示材料是「**框线在图像层、正文在文本层**」的混合排版，其内容本质是**文本而非图片** —— 走「提取图片」这条路本身就与数据结构相悖。已验证 `展示材料 1` 的正文全部存在于文本层（「来自不同报纸的头条」「旧城区发生两起命案」等均能命中）。

**后续如需交付展示材料**，应从**书页阅读或原文视图**入手（例如在原文视图内选择区域导出），而不是扩展图片提取。

## 三、验收要点

1. 导入 `样本 A.pdf` 扫描前 12 页，应能提取到 p3、p4、p5、p6、p10、p12 的图片；无名猎兽等真实插画完整保留。
2. 扫描结果中不应出现只有边框、内容近乎空白的图层（这类图是 PDF 的装饰框线，不是内容丢失）。
3. 导入 `样本 B`，扫描第 1–35 页，进度应持续前进，不再停在第 2 页。
4. 扫描速度与超时未放宽时相当，不出现每页固定等待数秒的情况。
5. 存在读取失败的图片时，状态文字应给出提示，不再静默跳过。
6. `npm run lint`、`npm run build`、`npm test` 全部通过。

## 五、数据与升级说明

- `ExtractedImageRecord.origin` 新增可选值 `"page"`，旧记录不受影响。
- 已导出的旧图片不会被自动清理；如需干净结果，可先删除项目内既有图片记录再重新扫描。
- 整页导出的图片体积明显大于内嵌图片（2 倍缩放 PNG），扫描大量页面时注意浏览器存储占用。

---

## 六、已知取舍

- 整页导出按页生成，无法只导出页面中的某一个方框；如需单独交付某块展示材料，可在导出后自行裁剪。
- 图片解码超时取舍在「大图不丢」与「不卡死」之间：15 秒内未解码的图片仍会被丢弃，但会计入失败数量并提示。
- 空白判定基于 32×32 采样，极端排版（例如内容仅有几个像素宽）可能被误判为空白。
